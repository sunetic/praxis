# 长任务可靠性

Praxis 有意保持长任务链路简单。原始用户请求是唯一的语义事实来源；运行时负责帮助模型可靠执行，而不是再生成一份可能偏离原请求的 LLM 规格。

## 运行流程

1. 执行器接收原始请求和可用工具。
2. 每次工具调用都产生配对的 `tool_start` 与 `tool_result`；成功、失败和超时结果都会作为证据保留。
3. 可恢复的执行错误可以进行有上限的重试。连续失败、取消、等待确认或达到截止时间时，以 checkpoint 结束本次运行。
4. 执行器生成一次候选答案。
5. 本轮实际调用过工具的任务只做一次完成审计：根据原始请求、已收集证据和候选答案判断结果。仅仅注册了可用工具，并不意味着必须调用或审计。审计器不能调用工具，也不会把修改指令送回执行器触发新一轮循环。
6. 运行时输出明确的运行状态与任务结果。

规划和调查都留在同一个执行循环里，避免分类器、审计修复和终稿生成器反复增加模型调用，却没有带来新证据。

## 证据与工具闭环

数据库任务中的关键结论应能追溯到用户输入或工具返回。运行时同时记录成功与失败调用，使模型可以调整策略而不重复同一种失败方式。

每个已经发出的 `tool_start` 都必须以一个 `tool_result` 结束。工具超时或执行器异常会转换成结构化失败结果，避免界面和任务日志无限等待。`AGENT_MAX_ELAPSED_SECONDS` 设置唯一的整轮运行截止时间，`AGENT_TOOL_TIMEOUT_SECONDS` 限制每次工具调用。

## 完成语义

执行是否停止与任务是否成功是两个不同维度：

| 字段 | 可选值 | 含义 |
| --- | --- | --- |
| `run_status` | `finished`、`awaiting_input`、`cancelled`、`error` | 本次执行为何停止 |
| `task_outcome` | `success`、`partial`、`blocked`、`unknown` | 用户请求是否真正达成 |

`completed` 作为兼容字段保留，只在 `task_outcome` 为 `success` 时才是 `true`。超时、重试耗尽、审计失败或取消都不能显示为完成。已有可用成果时，Praxis 会把它明确标成阶段性结果，列出尚未确认的缺口，并保存可续跑的 checkpoint。

## 上下文与并行

接近模型上下文窗口时，Praxis 会压缩较早内容，同时保留目标、证据、失败记录和近期交互。互不依赖的只读调用可以并行；有状态或高风险动作仍保持顺序，并可要求确认。

这些确定性机制属于常规测试。端到端任务质量、稳定性、耗时、工具调用量和 token 消耗，则通过重复运行的 [Eval](evaluation.md) 衡量。
