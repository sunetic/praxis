## 已实现的边界

- `app/services/agent/runtime.py`：单次 `Agent.run` 完整执行；自然文本或原生 deferred 输出；传入累计 usage 与主动时间预算；取消和异常原样向运行服务传播。
- `definitions.py`：不可变的运行身份、显式工具配置和一份短行为说明，不带任务阶段、完成协议或 SQL 固定流程。
- `tools.py`：配置能力与授权能力取交集，空集合没有工具；动态 JSON Schema 显式校验且不联网读取引用。
- `models.py`：从平台设置读取模型配置，复用原生模型连接，并提供 direct text request；连接关闭、参数错误和凭据脱敏有独立测试，不返回旧 LLMClient 响应字典。
- `store.py` / `app/models/agent_runs.py`：保存 run、原生消息、调用、审批和有序事件；以数据库事务取得会话执行权、执行租约及资源锁。会话只允许一个活跃 run，普通追加输入排队，显式停止并修改会取消当前执行；等待审批时的新输入使旧审批失效。
- `execution.py`：调用请求先落库再派发，结果先落库再交回模型。恢复时重新检查资源权限和目标；同一调用身份回读已知结果，不用参数去重不同调用。写入异常、超时、取消或结果提交失败时保留未知状态和资源锁。
- `service.py`：应用拥有后台任务，SSE 只是订阅。审批接口只记录决定，原生 deferred 继续执行原调用。等待审批不占主动时间预算；取消和服务关闭传递到执行任务。
- `events.py` / `app/api/agent_runs.py`：已挂载到主应用，提供原生会话、run、取消、审批和事件接口。事件可按游标重放；文字按最多 50 ms 或 4 KiB 合并，保持消息和 part ID，工具与结束事件前刷出，不展示 provider thinking。
- `application.py`：服务端解析 Agent 配置、资源范围及去重后的 Skills；CE 当前是显式的单用户身份，不信任客户端身份 header。Agent 的空工具集合保持为空，数据源绑定真实约束执行端。
- `datasource/agent_tools.py`：原生的资源列举和数据库读取工具；单条 SQL 语法校验、只读事务和有界结果预览。可见 SQL 错误返回给模型，不包裹旧 registry 或旧审批流程。

测试覆盖普通回答、文字与工具混合响应、多次业务失败、重复成功结果、参数纠正上限、工具越界、身份隔离、原生消息序列化、多项批准与拒绝、批准后权限复核、预算不重置、取消、usage 和 provider 字段保留。

持久化测试另外覆盖两个服务实例和多线程争抢执行权、重复提交与批准、同批批准和拒绝、服务重启后恢复原审批、SSE 断开不取消任务、游标重放、审批后的权限和目标变化、取消后的原生消息配对、跨会话资源锁、写入结果提交失败、过期所有者不能继续派发、文字合并及事件顺序。

原生取消令牌抛出 `RunCancelled`，外部 asyncio task 取消抛出 `CancelledError`；运行服务分别处理并保留原生历史。模型请求预算耗尽时，在恢复入口先拒绝派发，避免批准动作先执行、随后才发现无法继续请求模型。

## 仍未接通

当前故障恢复只做到安全中断和阻止误重放：过期租约变为 interrupted；结果未知的写入保留资源锁。还没有业务状态核对器或人工核对后的恢复接口，因此不能把它称为完整的崩溃恢复。等待审批的正常重启恢复已测试。

写入领域工具仍需提供真实的身份权限、目标版本、资源锁键和结果核对方式。`RegisteredTool` 要求写入工具使用 async、串行派发，避免不可取消的后台线程；业务实现也不能私自启动脱离调用生命周期的写入。跨系统没有 exactly-once 保证，锁住资源不等于外部操作已经回滚。

后续继续替换全部模型调用、各领域入口和前端协议，补齐中断核对与恢复、上下文压缩和领域集成，删除旧运行时，再执行完整任务、对话质量和浏览器验收。普通 Chat 和定时 Agent 执行使用新协议；领域构建界面仍使用旧协议。调度配置的自然语言编辑器、Function/Page 等入口还引用已失去 LiteLLM 依赖的旧代码，当前重构分支不能当作完整可发布版本。完整并发负载下的数据库写入、端到端事件延迟和浏览器渲染预算仍未验收。本批没有修改原项目的数据库。

## 原生上下文压缩与真实长对话

`context.py` 在 Pydantic AI 公开 `wrap_model_request` 接口中生成请求投影，不用 `before_model_request` 返回裁剪后的历史。锁定版本的后者会替换框架消息历史，因此不适合保存完整原始记录这一要求。普通 Chat、Scheduler 和单次长运行均由同一原生运行服务装配 ContextManager；尚未迁移的旧领域入口及其压缩器仍待删除。

容量计算包括当前指令、工具 schema、原生消息和输出预留，使用明确标注的 token 估算。保护原始用户目标、最新两个用户输入、近期完整消息组、系统消息和未决工具批次；工具调用与结果整组保留。保护区自身放不下时以 `context_limit` 结束，不丢掉用户目标换取请求成功。模型窗口、阈值、主回答输出预算、独立摘要生成预算及采样设置均进入 run 的不可变配置快照。

摘要不完整、来源引用无效或过大时不启动修复循环。若有已验证的旧摘要，保留它并单独记录未覆盖的新消息组；否则确定性裁剪完整消息组。事件区分 summary、partial_summary 与 trimmed，记录生成 token usage、完成原因、估算前后大小和耗时。引用校验只能验证消息身份与范围，不能证明摘要语义忠实；后者仍需真实对话评测。摘要作为历史材料传给主 Agent，不写入原始消息或提高为系统权限。

## 外部 Service 原生工具与真实 HTTP 写入（2026-09-21）

新增 integration/agent_tools.py，将 list_services 与 call_service 注册到同一个原生运行服务。普通 Chat 显式包含这两个工具；自定义 Agent 必须在实际工具目录中选择。服务访问来自当前获授权数据源的直接或 cluster 绑定，与 Run 冻结的 service_ids 取交集。会话可进一步缩小范围；空范围不解释为全部。停用服务、撤销数据源授权、解除绑定会在执行时重新检查，读取服务文档也不扩大知识库权限。没有重新注入旧 CallServiceTool 或调用 ChatService。

现有 Service 配置没有可验证的逐操作只读声明，因此通用 HTTP 调用都需要批准，包括 GET；服务目录查询无需审批。这里没有将 HTTP method 当成业务无副作用的证明。调用串行并使用服务资源锁；审批指纹包含原参数、绑定及连接配置/凭据的带密钥摘要。批准后再次读取配置并与记录的目标核对，再用这份快照发送请求。凭据不放进模型上下文、审批卡或工具结果。HTTP 回显中的已知凭据做脱敏，连接异常不返回原始异常字符串。

HTTP transport 明确不跟随重定向、不自动重试，响应边读取边限量，截断时不伪造完整总长度。422 等业务拒绝作为失败结果回到同一个 Agent；读超时、HTTP 500 等可能已产生副作用的情况标记 outcome_unknown，不再盲目重放。未知结果保存脱敏后的 HTTP 错误码、状态与诊断。成功及失败结果附上原调用实际批准的决定、操作者和时间，不靠模型推测谁批准了操作。通用 HTTP 尚没有外部状态核对协议；这里只验证保护未知结果，没有完成核对恢复。

### 真实调用发现并修复的参数问题

首次成功跑完的三组中，一次删除被拒绝后，模型给同一 DELETE 增加了 body 再请求。旧 transport 会静默丢弃 DELETE 的 body，而批准指纹包含 body，导致相同的实际 HTTP 动作弹出了第二张审批卡。该组虽然没有发出 DELETE，仍违反拒绝后不反复弹卡的要求，不能计作审批体验通过。

现在 GET/DELETE 携带非空 body 会在工具参数校验时被明确拒绝，早于审批与 HTTP；底层 transport 同样拒绝，不再丢弃参数。新增确定性用例重放“拒绝 → 增加无效 body → 恢复原参数”的序列，只有第一张审批，HTTP 发送为零，原参数重试读取既有拒绝。没有根据模型文字判断重试意图，也没有新增任务阶段或失败次数裁判。

## 原生数据库写入、审批与真实进程中断（2026-09-21）

新增 request_database_change 工具，与查询工具共用场景授权，由 DurableToolset 保存原始调用、请求批准并唯一派发。平台写入开关关闭时不发送写工具 schema，执行时仍检查当前权限。批准绑定原 SQL、目标连接、凭据及访问级别的 HMAC 版本；不让模型填写 approved，也不自动切换到管理员数据源。旧全局 confirmation_bypass 不用于这个原生入口。

旧 MySQL execute_query 会在连接丢失或解码失败时重新执行，不能复用于写入。新的 write_executor 使用单次新连接、不重试：本地校验一条支持的语句，服务端准备后执行，返回真实完成回执。MySQL 使用参数化 PREPARE/EXECUTE，避免驱动开启多语句能力时绕过单语句约束；流式丢弃返回行，不无限缓冲。PostgreSQL 也先准备同一语句，再执行并保留 command status。准备阶段失败作为未执行错误交回模型；进入执行后没有收到成功回执则保留 outcome_unknown，不能把任意 SQL 报错等同于没有副作用。取消也不承诺回滚。

这个边界参考了 [MySQL prepared statements 的单语句限制](https://dev.mysql.com/doc/refman/8.4/en/sql-prepared-statements.html) 和 [DDL 隐式提交说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。当前工具不支持 SQL 脚本、会话/事务控制和存储过程；尚不能把它称为旧 SQL 业务能力的完整替代。PostgreSQL 分支本轮只验证了驱动契约，没有真实 PostgreSQL 服务证据。

## Function 业务执行生命周期（2026-09-22）

Function 构建继续使用统一 Agent Run；本轮处理的是发布后调用，不增加 Function 专属 Agent。`RuntimeApplication` 现在持有一个 `FunctionRuntimeService`，HTTP 手工调用与 Scheduler 共用该实例。API 不再为每次请求创建和关闭临时 Runtime，因此调用可以用预先生成的 `run_id` 被另一请求准确停止。Scheduler 只关闭自己创建的 Runtime；应用共享实例由应用 shutdown 统一收尾。

调用开始时在短事务内读取 draft 或 release 快照并创建 `FunctionRun`，随后关闭控制库 Session，再启动受 Runtime 持有的子进程。结束状态使用新 Session 单独结算。运行记录新增完整 `output_payload` 和 `error_code`；成功、失败、超时和取消不再只剩截断摘要。显式取消终止对应进程组，原调用请求和取消请求得到同一 `cancelled` 事实。取消前已经完成的数据库或外部动作不能回滚，返回信息明确保留这一限制。

应用关闭造成的中断与用户取消分开记录。正常 shutdown 回收子进程后写入 `interrupted/execution_owner_lost`；新应用启动时也会收敛遗留的 running 记录，提示外部结果可能未知，不伪装成取消成功或自动重试。

Function 列表页在发起调用前生成 run ID，运行中可停止该次调用；历史状态支持 cancelled。这里没有修改 Chat 页面或构建工作区布局。普通业务执行仍是进程生命周期隔离，不是安全沙箱；文件、环境和网络能力边界还需单独完成，文档不把当前实现写成安全隔离。

新增服务与 API 覆盖共享 Runtime、完整结果落库、直接任务取消、HTTP 取消以及进程回收。Function、Runtime、Scheduler 和架构相关回归为 **98 项通过**；Function/Scheduler 前端定向为 **11 项通过**，类型检查通过。项目级 ESLint 仍报告既有规则债务，定向修改没有以放宽规则处理。
